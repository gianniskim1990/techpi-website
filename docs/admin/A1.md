## 1. What A1 does

The custom TechPi Admin (the approved Dashboard, lists and Editor) now has a server side. For the isolated M0 demo
collection only, an administrator can:

1. sign in through Cloudflare Access (checked by the Worker on every request);
2. open **Test content**, which lists the demo entries read live from GitHub through the Worker;
3. edit the demo article (title, summary, Markdown text, cover alt text, SEO title and description; EN and an optional EL);
4. **Save draft**: the Worker validates the entry, commits it to the branch `cms/m0-demo/<slug>` and opens **one**
   draft pull request into `feat/techpi-admin-m0`. Later saves add commits to the same branch and PR.

Publishing is not available: the Publish button is disabled with an explanation. Nothing can be merged from the admin.
`main` is never written: the draft base cannot be `main` in this version, and every write goes to a `cms/m0-demo/` branch.

The other sections (Dashboard, Case studies, Articles, Pages, Media, SEO, Settings) are still the read-only snapshot
from the prototype, and are labelled as not connected. The 18 case studies and 7 articles were **not** migrated.

## 2. Architecture

```
Browser (custom admin, connect-src 'self')
   │  same-origin fetch to /api/*, header X-TechPi-Admin: 1, no credentials of its own
   ▼
Admin Worker (admin/worker)
   index.js   every request: Cloudflare Access check (auth.js) → API same-origin check → api.js, or static file
   auth.js    ctx.access audience + identity, email allowlist; same-origin / CSRF checks
   api.js     /api/session, /api/m0-demo, /api/m0-demo/<slug>, POST /api/m0-demo/<slug>/draft
   github.js  GitHub App JWT (RS256, WebCrypto) → installation token (this repo, 3 permissions), cached; REST calls
   ▼
GitHub REST API (gianniskim1990/techpi-website only)
```

| File | Purpose |
|---|---|
| `admin/shared/m0-content.js` | Collection paths and the field rules; used by the Worker (authoritative) and the UI (instant feedback) |
| `admin/src/app/lib/api.js`, `session.svelte.js` | The UI's API client and the signed-in session |
| `admin/src/app/views/TestContentList.svelte`, `DraftEditor.svelte` | The connected list and editor |
| `admin/index.html` | The custom admin (was `prototype.html`) |
| `admin/sveltia-m0.html` | The legacy M0 Sveltia CMS (was `index.html`); kept until section 6 is done, then removed |

## 3. Security controls

**Authentication (every request: pages, files and API).** The Worker reads `ctx.access` (set only when Cloudflare
Access ran for the request), requires the configured audience (`ACCESS_AUD`), gets the identity from Access and checks
the email against `ADMIN_EMAILS`. Without configuration it answers 503 to everything. Headers such as
`Cf-Access-Authenticated-User-Email` or any email, role, repository or branch sent by the browser are ignored.

**Cross-origin and CSRF.** API requests must carry `X-TechPi-Admin: 1` (a custom header cannot be sent cross-origin
without a CORS preflight, which the Worker never approves); `Sec-Fetch-Site`, when present, must be `same-origin`;
writes must have an `Origin` equal to the admin's own origin and a JSON body. Responses carry `Cross-Origin-Resource-Policy:
same-origin`, `frame-ancestors 'none'`, `X-Frame-Options: DENY`, no-store and noindex.

**GitHub credentials.** The browser never receives a GitHub credential and never calls GitHub (`connect-src 'self'`;
only the legacy Sveltia page may reach `api.github.com`). The Worker signs a 9-minute App JWT and requests an
installation token restricted to `techpi-website` with `contents: write`, `pull_requests: write`, `metadata: read`.
Tokens are cached in memory until 5 minutes before expiry; a 401 refreshes once. Tokens, keys and headers are never
logged or returned; error logs contain only method, path and status.

**Server-side scope.** The repository is a constant. Branch names and file paths are derived from the validated slug
(`^[a-z0-9]+(-[a-z0-9]+)*$`). The only write operations are: create or reset a `cms/m0-demo/<slug>` branch, update one
file on it, and open a draft PR into the base branch. There is no publish, merge or delete endpoint. The base branch
(`CONTENT_BASE_BRANCH`, default `feat/techpi-admin-m0`) is refused if it is `main` or a `cms/` branch.

**Conflicts.** Every save sends the Git blob SHA of the version the editor loaded. If the draft (or, before the first
save, the base) has changed, the save is refused with 409 and the editor offers to reload; GitHub's own SHA check is
a second guard. Repeated saves reuse the open PR; a duplicate-PR race is handled by re-reading it.

**Validation.** The Worker validates every save (unknown languages and fields refused, required fields, lengths
matching the Astro schema, cover file pattern and alt text) and writes a canonical JSON file. The Astro build validates
the same files again.

## 5. Test results (2026-10-20)

`cd admin && npm test`: **41 tests, 41 pass** (17 API, 4 GitHub auth, plus the M0, Worker and validation suites).

| Required case | Test | Result |
|---|---|---|
| Valid administrator | session returns the Access email; full load–edit–save flow | pass |
| Missing Access identity / wrong audience / non-allowlisted user | 403 on session, list and save; zero GitHub requests | pass |
| Missing or invalid GitHub App configuration | missing settings named, 503; unreadable key, wrong App ID, wrong installation: clear 503 messages | pass |
| Expired installation token | token reused while valid; after expiry, refreshed once transparently | pass |
| Cross-origin write | foreign or missing `Origin`, missing header, `Sec-Fetch-Site` cross-site or same-site → 403; form or text bodies → 415 | pass |
| Unauthorised branch or repository | `branch`, `repo`, `path` in the request ignored; traversal and invalid slugs → 400; other collections and raw repo paths → 404; no publish endpoint; base `main` refused | pass |
| Conflicting or stale update | draft changed elsewhere → 409, newer change kept; base changed before first save → 409, no branch; GitHub 409 on write → 409 | pass |
| GitHub API failures | 5xx → 502, network failure → 502, 403 → 503 "permission"; nothing saved | pass |
| No writes to `main` | every write is on `cms/m0-demo/m0-sample-article`; `main` and the base unchanged; nothing merged | pass |
| Repeated saves | one draft PR, updated; unchanged save writes nothing | pass |
| No credentials in responses | no `ghs_`, private key or `Bearer` in any API response | pass |

**Public website.** `npm run check`: 0 errors, 0 warnings. `npm run build` with all content validators: 0 failures.

## 6. Owner setup for the real GitHub test (not done; needs the owner)

Nothing below was performed. These are the steps for the owner; the admin then runs locally against real GitHub.

1. **Create the GitHub App** (GitHub → Settings → Developer settings → GitHub Apps → New GitHub App), on the
   account that owns the repository:
   - Name: e.g. `TechPi Admin`. Homepage URL: `https://techpi.eu`.
   - **Webhook: untick "Active"** (none is needed).
   - **Repository permissions:** Metadata **Read-only**; Contents **Read and write**; Pull requests **Read and write**.
     Everything else: No access. No organisation or account permissions. No events.
   - Where can it be installed: **Only on this account**.
2. **Install it only on `techpi-website`** (App page → Install App → Only select repositories → `techpi-website`).
3. Note the **App ID** (App settings page) and the **installation ID** (the number at the end of the URL
   `…/settings/installations/<id>`). Neither is secret.
4. **Generate a private key** (App settings → Private keys). Keep the downloaded `.pem` file private. It must never be
   committed, pasted into chat, or put in a `vars` entry.
5. **Local test with real GitHub** (still no deployment). Two git-ignored files in `admin/`:
   - `wrangler.local.jsonc`: copy of `wrangler.local.example.jsonc` with the App ID and installation ID filled in. It
     simulates Cloudflare Access as `admin@example.test` and contains no secret.
   - `.dev.vars`: **only** `GITHUB_APP_PRIVATE_KEY`. Create it in PowerShell without opening or displaying the key
     (replace the path with where the `.pem` file is):
     ```powershell
     Set-Location C:\Projects\techpi-website\admin
     $pem = "C:\path\to\your-app.private-key.pem"
     $key = ((Get-Content -Raw -LiteralPath $pem).Trim() -replace "`r?`n", '\n')
     [IO.File]::WriteAllText("$PWD\.dev.vars", "GITHUB_APP_PRIVATE_KEY=`"$key`"`n", [Text.UTF8Encoding]::new($false))
     Remove-Variable key, pem
     ```
   - Check, without printing the key: `node scripts/check-local-config.mjs` (offline) and then
     `node scripts/check-local-config.mjs --github` (read-only: gets a token and reads the demo file; writes nothing).
   - Run `npm run build` and `npx wrangler dev --config wrangler.local.jsonc`, open `http://127.0.0.1:8787/#/test-content`,
     edit the demo article, Save draft once, and check that one draft PR into `feat/techpi-admin-m0` appeared and `main`
     is unchanged. The PR is public and contains dummy content only.
   - Never paste the key into a chat, an issue or a config file other than `.dev.vars`. Keep the `.pem` outside the
     repository folder.
6. For a later deployment (separate approval): the key goes in with `wrangler secret put GITHUB_APP_PRIVATE_KEY`, the
   IDs as variables, and the Worker behind a Cloudflare Access application with the administrator allowlist.

`GITHUB_API_BASE` exists only for the local mock; the Worker ignores it unless it is `http://127.0.0.1:<port>`.
