## 2. Security model

| Requirement | How it is met | Verified |
|---|---|---|
| Admin login | Two layers: Cloudflare Access in front of the admin Worker, then a GitHub fine-grained token entered in the CMS | Access gate: locally in workerd with Wrangler's documented `access.dev` simulation. Real Access and real GitHub sign-in: **not verified (owner setup)** |
| Server-side authorisation | The Worker checks `ctx.access` (undefined unless Access authenticated the request), the Access audience, and an email allowlist. Every request, including static files, goes through it (`run_worker_first`) | Unit tests and local workerd end to end |
| No privileged secrets in the browser | There are none to expose: no OAuth app, no client secret, no GitHub App key. The Worker holds no credential | Code review and secret scan |
| Token scope, expiry, revocation | A fine-grained token for **this repository only**, with Contents and Pull requests read/write, and an expiry. Revocable at any time in GitHub settings. Sveltia stores it in the browser's local storage on the admin origin, protected by the strict CSP and by Access | Documented by Sveltia; not exercised (owner token) |
| Unauthenticated requests cannot modify content | Writes go only to GitHub's API and need a token with write access to this repository. The Worker has no write endpoint (405) | Tested (405, 403, 503) |
| A draft cannot silently publish | Editorial Workflow saves each change on its own `cms/<collection>/<slug>` branch as a draft pull request; only Publish merges it. **Server-side enforcement needs a branch rule on `main`** (section 5, step A): without it, the CMS's Asset Library would commit straight to `main` | Rule not set yet (owner) |
| Confidential drafts | **Not protected today.** The repository is public, so draft branches and pull requests are public, and branch previews on workers.dev are public (though `noindex`). See section 5, steps E and F | M0 used dummy content only |
| No credentials in Git | Secret scan of every committed file and of the admin build; the only emails are reserved `example.test` test identities; `ACCESS_AUD` and `ADMIN_EMAILS` are empty in the repository and set at deploy time | Scan clean |

## 4. Architecture findings

- **Sveltia works with this stack.** It is a static app, so it needs no server runtime and has no Cloudflare or Astro
  compatibility issue. GitHub sign-in by fine-grained token is officially documented. PKCE is not available, because
  GitHub has put it on hold. OAuth needs an OAuth app (classic `repo` scope, i.e. all of the owner's repositories,
  with no expiry) and a token-exchange server, so it is less secure for a single administrator. **Token sign-in is the
  recommended method**; Sveltia's own authenticator Worker can be added later if a non-technical second user appears.
- **Editorial Workflow (0.229.0):** draft pull requests per entry, statuses as labels, merges pinned to the reviewed
  commit, auto-merge waiting for required checks, Discard closes the pull request. Today's documentation describes
  extra publish-time checks that may be newer than 0.229.0; publication control must rest on the GitHub branch rule,
  not on client-side checks.
- **Content shape:** confirmed from the pinned source: `single_file` writes `{ "en": {...}, "el": {...} }` and omits a
  locale that has no content, so English-only entries are valid.
- **Images:** entry-relative images work with Astro's `image()` and build-time optimisation. Uploads are re-encoded to
  WebP and size-limited by the CMS; the build validator is the authoritative check. The upload dialog itself was not
  exercised (it needs a real repository session).
- **Gaps for the full CMS:**
  - Existing content must move from TypeScript to JSON/Markdown with schemas, keeping the output byte-identical (M1).
  - The Asset Library commits to `main` directly unless the branch rule exists.
  - The CMS offers optional AI translation only if a user adds their own API key in its settings. No key is configured;
    this is a policy decision.
  - Route lock and unpublish-with-redirect are still to be built (M3).

## 5. Owner setup required (not performed; each needs explicit approval)

A. **Branch rule on `main`** (GitHub → Settings → Rules → Rulesets → New branch ruleset): target the default branch;
   block force pushes and deletion; require a pull request before merging; require the status check
   **Workers Builds: techpi-website**; no bypass actors. Also Settings → General → Pull requests → **Allow
   auto-merge**. This is the server-side guarantee that nothing reaches production without a passing build and a
   deliberate merge.

B. **Fine-grained token for the M0 test** (GitHub → Settings → Developer settings → Fine-grained tokens): resource
   owner your account; only the `techpi-website` repository; permissions **Contents: Read and write** and **Pull
   requests: Read and write**; expiry 30 days. Keep it in your password manager; never paste it into a chat.

C. **M0 end-to-end test** (after A and B): `cd admin`, `npm ci`, `npm run dev:m0`, open the local URL, **Sign In with
   Token**, open "M0 sample article", change the title, Save. Expected: a branch `cms/m0-demo/m0-sample-article` and a
   draft pull request against `feat/techpi-admin-m0` appear on GitHub, a Cloudflare preview builds for that branch, and
   `main` is unchanged. Then **Discard** in the CMS (closes the pull request and deletes the branch). Do not Publish
   during M0. Revoke the token afterwards if it will not be reused.

   Why `dev:m0`: the CMS lists entries from one branch only. Plain `npm run dev` reads `main`, where the demo content
   does not exist until PR #27 is merged, so it correctly lists zero entries (the 2026-10-20 "zero entries" report).
   `test/config.test.mjs` now checks that the configured branch contains every collection's entries.

D. **Cloudflare Access for the admin** (only when deploying, M2): Workers & Pages → `techpi-admin` → Access → Protect
   this Worker → **All traffic** → policy limited to your email. Then set the Worker variables `ACCESS_AUD` (the
   application's audience tag) and `ADMIN_EMAILS` in the dashboard, not in the repository.

E. **Private draft previews:** Workers & Pages → `techpi-website` → Access → Protect this Worker → **Previews only** →
   policy limited to your email. Branch and pull-request previews then need sign-in; production `techpi.eu` is not
   affected. Verify afterwards that `techpi.eu` still loads without sign-in.

F. **Repository visibility:** while the repository is public, every draft branch, pull request and uploaded image is
   public on GitHub before publication. Use the CMS only for non-confidential content, or make the repository private.
   On GitHub Free, rulesets are not available for private repositories, so a private repository keeps step A only with
   GitHub Pro (USD 4 per month).
